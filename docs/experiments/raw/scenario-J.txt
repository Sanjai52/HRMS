Scenario J — catalog outage: fail-closed logins/search, shard-local writes survive to the
local deadline, writes resume after recovery
Date: 2026-10-19 (morning session)  |  Commit: f82fb91 + this task's fixes (shipped with this
file; see git log)
Setup: full stack (pg-catalog, shard-1..4, redis-kv, redis-queue) up; APIs :4000/:4002/:4003
and worker :4001; NGINX not involved (direct :4000); live HR session; fresh employee created
per round via invite -> accept -> onboard and its projection confirmed before the stop.
Method: real HTTP against api :4000; `docker compose stop pg-catalog` / `start pg-catalog`;
exact curl outputs; timing model = registry heartbeat every 5 s, TTL 30 s, margin 10 s =>
local write deadline = last successful heartbeat send + 20 s (D-002).
Raws: scenario-J-run.txt (round 1, pre-fix), scenario-J-run2.txt (round 2, full run),

-- round 1 (pre-fix build; scenarios-J-run.txt) --
Two mismatches found and fixed in the owning tasks before recording any pass (T20 rule):

1. D-002 intent vs built routing path: `selfEmployeeId` + `shardFor` re-read the catalog per
   request, so a catalog outage killed writes at 503 DEPENDENCY_UNAVAILABLE before the fence
   could run, and the local deadline was unreachable over HTTP.
   Fix: `RoutingCache` (core) + API wiring — the routing map and user->employee identity are
   snapshotted in-process and refreshed on each registry heartbeat; a failed refresh keeps the
   last snapshot, and the registry's local deadline bounds how long it may be trusted.
   Files: packages/core/src/routing-cache.ts (+ test/routing-cache.test.ts),
   apps/api/src/routing-cache.ts, apps/api/src/directory/self.ts, apps/api/src/registry.ts.
2. D-003 lease window: the ID issuer zeroed its local validity on the first failed renewal
   (`validUntil = 0`), so ID-allocating writes failed with 503 ID_LEASE_UNAVAILABLE ~5 s after
   the outage started — the registration deadline (~20 s) never got to bind, contradicting
   D-003 ("ID generation stops by approximately 45 s after the last successful
   lease-renewal ... D-002 registration validity stops all shard writes earlier, at
   approximately 20 s").
   Fix: a failed renewal no longer cuts the window; `next()` fails closed at
   last-success + TTL - margin (~45 s). Files: packages/core/src/leases.ts
   (+ test/id-issuer.test.ts with fake timers).
3. Worker crash during the same stop: stopping pg-catalog killed an idle pool client and the
   worker had no `'error'` listener on its pools -> unhandled 'error' event, process exit
   (`57P01 terminating connection due to administrator command`, worker-fixJ.log). The API
   pools were already guarded; the worker's were not.
   Fix: `guardPool` in apps/worker/src/pools.ts logs and continues; next query acquires a
   fresh client.

-- rounds 3-4 (recovery precision; scenario-J-recovery.txt) --
Round 3 fixed my probe: `docker exec` cannot read a stopped container, so the baseline must be
captured before the stop. (Its writes-resume number — 4.938 s after start, within one
heartbeat — was still valid because a successful write requires a heartbeat success within
the preceding 20 s.)

Interpretation: after the fixes, all four briefed J behaviors hold on the live stack — logins
and catalog-backed searches fail closed in ~2 s (dependency connect timeout), shard-local
writes continue for the whole local deadline and stop with REGISTRATION_EXPIRED -> 503
GATE_CLOSED at last-heartbeat + 20 s, snapshot-routed reads stay available, and post-recovery
writes resume within one heartbeat of the catalog accepting queries. The ID lease no longer
preempts the registration deadline (D-003 vs D-002 ordering restored), the routing snapshot
removes per-request catalog reads from the write path, and the worker survives catalog stops.
