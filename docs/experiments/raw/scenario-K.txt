Diagnosis (a regression introduced by the J routing snapshot, 482e75c): the identity snapshot
is refreshed on the 5 s registry heartbeat, so for up to 5 s after a directory row lands
(onboarding -> first self-service action) `selfEmployeeId` returned null and the route answered
404 "No employee record for this account yet" (apps/api/src/routes/leave.ts:70). The fence test
runs that flow in ~2 s, inside the stale window; the full suite had not run since the snapshot
landed, so K was the first run to expose it. Before the snapshot, the lookup was a per-request
catalog read and could not go stale.

Fix (in `RoutingCache.employeeIdOf`, packages/core/src/routing-cache.ts): a miss re-reads the
identity once, throttled to one read per second. Known users still resolve from the snapshot
without touching the catalog; during a catalog outage a miss throws (routes surface a dependency
error — fail closed), and unknown-user traffic cannot amplify into one full read per request.
New core tests: miss re-read (fresh employee visible immediately) and throttling
(packages/core/test/routing-cache.test.ts, 6/6).

Fix verification (scenario-K-missrefresh-repro.txt): onboard -> run-dispatcher -> IMMEDIATE
  POST /leave/requests: HTTP 201 after 0.057333 s (was 404)
  POST /attendance/check-in: HTTP 201 after 0.081074 s
  wall time from dispatcher drain to leave response: 0.216 s — far inside the old 5 s window.
